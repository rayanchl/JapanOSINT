## What this batch is, and why it is not a new discovery pass

Batch 46 asked each ArcGIS service root already in the tree for its own
directory (`?f=json`) instead of requesting the one path somebody happened to
know, and that produced 899 candidate layers, 819 of which probed PASS. Three
filters then ran — dedupe the `arcgis`/`ArcGIS` and MapServer/FeatureServer
spellings, a 50-record floor, drop pure cartography — leaving **456 candidates
on 157 roots**. Batch 46 shipped **164** of them, at two per root against a
165-row target.

That cap was a batch-size decision, not a quality one. These 290 rows are the
remainder of the same probed pool, through the same filters and the same live
probe. No root contributes more than five, because the DISCOVERY cap was five
per root, so the per-root selection cap was buying almost nothing.

## Every batch-46 lesson applies, and was applied

These rows were generated by the same scripts under the same rules, so the
measurements batch 46 made are the measurements behind these 290:

* **Attribution is keyed on the whole service ROOT, never the host.**
  `services1.arcgis.com` is a multi-tenant front for hundreds of unrelated
  organisations, distinguished only by a 32-character org id in the PATH — the
  defect that named a Wyoming EMS layer after a Wakayama City traffic dataset.
  Where the publisher cannot be established the row names the HOST, which is a
  fact about where the data came from rather than a guess about whose it is.
* **Each layer's `objectIdField` and `maxRecordCount` are its own**, not
  `OBJECTID` and not a constant; `resultOffset` is a record offset so
  `page_size` belongs on it, and a cycling layer carries
  `orderByFields=<oid> ASC` because ArcGIS promises no stable ordering without
  one.
* **`returnCentroid` is POLYGON-only.** ArcGIS says so with HTTP *200* and a
  216-byte error body, which is why 18 batch-46 polyline rows came back
  `PATH_UNRESOLVED` from a rule tested on four layers that happened to all be
  polygons. Re-measured per geometry type: polygon rings cost 64x the payload
  and a centroid 1.7% of that, while polyline paths cost 1.3–9.3x, so polylines
  keep full geometry.

## What this batch found on its own

* **Two rows exceed the engine's 20-second default** and carry
  `timeout_ms = 90000`: measured at 37.5 s and 28.3 s. A row that times out
  stores nothing and says so via `collector-fetch-failure`, which is honest and
  still useless, so the timeout is set from the measurement rather than left at
  a default that cannot serve them.
* **One true duplicate**, on `ADHP`, dropped by `batch_exclusions.py`. Worth
  contrasting with batch 46's "airspace" hit, which was a FALSE positive: the
  exclusion matched a `record_type` literal rather than an endpoint. The check
  earns its keep in both directions.
* **`page_resume` had never reached `gen_hp_batch.py`'s opt table**, so the
  first generation run rejected every row that needed it as an unknown opt.
  `page_resume`, `window_days` and `window_from` are in `STR_OPTS`/`INT_OPTS`
  now. This is the third engine field to be missed the same way, after
  `page_walk`: when you add an `hp_source` field, add it there in the same
  change.

`audit_batch_reachable.py`: **0 of 290 rows can never run** — every row
declares an interval, so rule 3 is satisfied.

**The emit audit has been run, and all 290 rows account for themselves.** A
shortfall that is not a cycle is a question, so every row that does not store
exactly its upstream count was chased:

| 1 | EMITS_NOTHING — `gis.charttools.noaa.gov` FLAPS: it served 371 of 371 twice and answered HTTP 200 carrying `code=500 "Could not find service. Service may be stopped or it may not be configured."` twice, within ten minutes. The engine reports `rc=-1` and the error document, which is correct; the row is not the defect |

That last one is why a single verdict is not a diagnosis. A direct `--run`
stored 371 while the audit said nothing reached `intel_items`, which made the
GATE and the ENGINE disagree — the dangerous direction — and reproducing the
audit's exact invocation showed the cause was neither of them. A row "fixed" on
the first reading would have been changed for no reason.

The emit audit is rule 4 and 4b, and it is the reading that outranks the probe
in both directions. Run it with **low concurrency and never beside another
sweep on the same hosts**: 37 hosts carry 290 rows, so a parallel audit
concentrates requests exactly where ArcGIS will answer 429 — the mistake
recorded under the cycle-health sweep in CLAUDE.md, and again under the page-2
sweep, which saturated this container's own egress tunnel at ten jobs.
