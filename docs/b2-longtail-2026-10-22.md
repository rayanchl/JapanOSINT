# B2's long tail, measured — 2026-10-22

Open item B2 ended with a short list of rows whose publisher had moved the data
and for which no path had been established. Each one was asked what its
publisher ACTUALLY serves, rather than probed for a path we could name. The
answer was an engine affordance twice over.

Every number below is a reading taken on 2026-10-22 through either the engine's
own client (`./bin/japanosint --run`) or `curl` with the engine's `JO_USER_AGENT`.

## The three rows that ship

### PMDA — the annual approval workbook, whose sheets are MONTHS

The pivot's path (`/PmdaSearch/iyakuSearch/Result?keyword=`) answers **404** for
a real drug name (アスピリン) and for an impossible one alike. The live form at
`/PmdaSearch/iyakuSearch/` is `POST /PmdaSearch/iyakuSearch` with `nameWord`
plus two radio groups, and it answers the FORM PAGE AGAIN for every POST that
can be constructed from here — 87,697 bytes each time, 0 result tables:

* plain POST with `nameWord` + both radios + `ListRows=100` + `btnA=検索`;
* the same with a session cookie (`JSESSIONID`) obtained from a GET of the form;
* the same with a `Referer` of the form page;
* the same with `btnA.x`/`btnA.y`, since `btnA` is `type="image"` and a browser
  submits coordinates rather than a value;
* the same with the display-column checkboxes set.

So the register is not reachable through that search. What PMDA publishes as a
FILE is the annual approval list: `review-information/p-drugs/0040.html` is
2026年度 and carries `/files/000281578.xlsx` (32 KB), whose attachment id
changes with every edition — the `index_url` / `index_href_must` case.

Its four worksheets are **承認品目5月分, 6月分, 8月分, 9月分** (July is the
publisher's own gap) and a new one appears every month. All four have identical
geometry: a title line, a blank line, then a header whose cells carry quoted
CRLFs and so span THREE physical lines of the converted CSV — so
`csv_skip_lines = 5` lands on the first data row of every sheet, measured per
sheet rather than assumed. `csv_no_header = 1` because the header's names live
in merged multi-line cells (the ECB workbook's lesson).

Records stored: 95, the sum of the four sheets' data rows (11 + 29 + 23 + 32)
exactly. No header row among them; one is a blank spacer row the publisher
leaves inside a sheet, which keys on itself and so is one record for ever.

### Assemblée nationale — 19,165 JSON documents in one ZIP

`/dyn/recherche?texte=` answers **404** for `Renault` (64,553 bytes) and for an
impossible string (64,562 bytes) alike, and the homepage carries **no search
form at all** — the site renders its search in the browser.

`data.assemblee-nationale.fr` is the publisher's own open-data site and its
written-questions page declares exactly four links, two formats of one file:
`/static/openData/repository/17/questions/questions_ecrites/Questions_ecrites.json.zip`.
That ZIP is 50,197,713 bytes and holds **19,165 entries**, one JSON document per
question, each `{"question": {...}}` with `uid`, the subject heading, the
deputy and their group, the ministry, the Journal officiel issue and page, and
the full text.

Measured through the engine: 19,165 emitted / 19,165 stored in one request, 126
s, every record titled, 3 undated (the JO has not published them yet).

An earlier attempt reported `rc=-1 records=1 bytes=0 requests=2`, which is this
container's egress rather than the host: the 50 MB download takes 73 s at
683 KB/s and the proxy was saturated by a registry sweep running beside it.

### Kanpō — the search went behind a paywall, the gazette did not

`search.npb.go.jp/kanpou/search.html?q=` answers 404, and
`search.npb.go.jp/kanpou/` redirects to
`/kanpou/auth/login/LoginStartUp.form`. It is a paid MEMBER ACCOUNT, not an API
key, so there is no `key_env` that would open it.

But `kanpou.npb.go.jp` redirects to `www.kanpo.go.jp`, which publishes the last
**ninety days** free, with a table of contents per day at
`/{YYYYMMDD}/{YYYYMMDD}.fullcontents.html` listing every notice with its full
title, the issuing ministry and its notice number, across 本紙 (the main
edition), 号外 (the extra), 政府調達 (government procurement) and 特別号外.

Two things had to be measured rather than assumed:

* **`base` must be left UNSET.** The hrefs are relative to the DAY'S DIRECTORY,
  and with `base` unset the engine resolves them against the page it fetched,
  which is that directory. Declaring the host instead — the obvious thing, and
  the first thing tried — resolved every notice to
  `https://www.kanpo.go.jp/20261022h01813/…`, a 404 for all 25 of them, with
  the record count and the run line perfectly healthy.
* **The day's 43 anchors become 25 records** because several notices share one
  gazette page. That is the engine's anchor policy, not a loss: each record
  keeps the strongest label as its title and the others as `other_labels.N`, and
  9 of the 25 carry one. A record count alone would read 43 → 25 as a collision
  to fix.

`date_back = 4` with `date_step = "d"` is what makes a daily row work on a
gazette: nothing is published at a weekend or on a public holiday, so a run on a
Sunday walks back to Friday rather than reporting an empty day.

## The rows that stay registered and failing

The standing decision is to keep every one of these and disclose, rather than
remove them. Each files one `collector-fetch-failure` record per (source,
entity), upsert-keyed, and the source pages read the reason and the remedy back
beside the status.

* **`JP_PMDA_APPROVALS`**, **`FR_ASSEMBLEE_NATIONALE`** and
  **`JP_KANPO_GAZETTE`** — the three dead pivots above. Their descriptions now
  carry the measurement and name the row that stands in for them.
* **`JP_MHLW_LABOUR_VIOLATIONS`** — no replacement was found, and the search for
  one is worth recording. The authored index answers 404 (with the ministry's
  **49 KB custom 404 page**, so read the status and not the byte count). The
  ministry's own site search is a **Google Custom Search**
  (`cx=005876357619168369638:ydrbkuj3fss`), which is Google's index of the
  ministry rather than the ministry's register — the reason it is not
  re-pointed there. And the labour-standards section of the ministry's own
  sitemap (`/sitemap/index.html` → `roudoukijun/index.html`) lists no
  public-disclosure page: its links under 公表 / 違反 / 監督 / 送検 are the care
  services disclosure system, the labour bureau directory, a chatbot and a
  notice about inspectors' uniforms.
* **`WORLDBANK_CONTRACT_AWARDS`** — **unmeasured, not dead.** Its Socrata API
  answers 404 outright now (it was "empty with no query" in the earlier
  reading), the portal has moved to `financesone.worldbank.org` (200), and
  `datacatalogapi.worldbank.org` answered **429 Rate limit is exceeded** to
  both attempts from here, 40 s apart. That is a reading of this afternoon, not
  a verdict about the dataset.
* **`AT_PARLAMENT_RECORDS`** — still not shipped, for the reason B2-bis gave:
  its index has no stable ordering and it ignores `pageSize` (3 rows asked,
  100,000 rows and 58 MB served). One measured sort parameter away.

## What generalises

* **One fetch buys a container, and reading one thing out of it is a discard at
  a seam.** Two unrelated publishers do this — a workbook whose sheets are
  months, an archive whose members are records — which is the argument for
  `xlsx_sheet_all` and `zip_all_entries` as engine fields rather than two
  bespoke collectors.
* **A notice nobody acts on is not a disclosure.** The engine's
  `zip-extra-entries` notice had been naming the Assemblée nationale's loss for
  as long as the row existed, and its suggested remedies ("a named-entry read,
  or one row per member") do not reach 19,165 members.
* **A comment claiming an honest failure is not one.** HP_XLSX set `out = -1`
  on a workbook it could not convert, three lines above an
  `out = st.emitted` that overwrites every mode driver's return. A workbook
  that would not convert at all reported `rc=0 records=0`.
* **A relative href resolves against the page, not the site.** Declaring `base`
  as the host is the intuitive thing and it broke all 25 links while every
  number stayed green.
