# Source pages revamp — audit and plan (2026-10-11)

Status: **ACCEPTED 2026-10-12 and implemented on `plan/source-pages-revamp`**
(all four phases; the five open decisions took the defaults stated in §2).
The "as built" section at the end records where each part landed and what
differs from the plan.
Companion data: `collector-census-2026-10-11.tsv` (342 collectors as the
binary registers them) and `hp-table-census-2026-10-11.tsv` (308 hpengine
tables, how many rows each holds and whether the file names a collector).

Both house rules apply to a UI as much as to a collector: the page displays
exactly what the server obtained, says in-band how much of it is shown, and a
missing fact renders as "not measured", never as a default.

## 1. Audit — what the source pages show today, and where it comes from

### 1a. Three places show "a source", none of them the whole picture

| surface | route | data | what it can say |
| --- | --- | --- | --- |
| Console → Sources (`SourceDashboard.jsx`) | `/console/sources` | `GET /api/sources` = raw `SELECT * FROM sources` | name, type, category, status, records, response time, last check, last success, 7 stat tiles, 3 charts, a "Data Pipeline" strip, 3 dropdown filters, expandable row with "Recent Fetch Logs" |
| Intel → source (`IntelSourceItemsPage.jsx`) | `/intel/sources/:id` | `GET /api/intel/sources` (whole list, 18,883 rows, to find one), `GET /api/intel/items?source=` | stored items, geocoded, awaiting geo, last fetched, latest record, category, ttl, upstream link, item search, **Run now** |
| Probe detail popover (`SourcesPanel.jsx`) | button on `/console/sources` | `GET /api/status` (≈20 MB, ≈8 s) | per source: sched state (declared/effective interval, backoff, quarantine), trust grade, credential env vars, probe request/response, intel counts |

### 1b. The dashboard is built on a table nothing writes

`sources.status / last_check / last_success / response_time_ms / records_count`
are seeded once by `db_seed_sources()` (`core/db.c:119`) with `status='pending'`
and **no C code updates them afterwards** (grep across `native/` finds only the
probe route writing `probe_*` columns). Consequences, all visible today:

* every one of 18,883 rows is `pending`, `0` records, `-` response time, forever;
* the four status tiles and the status pie are a picture of the seed, not of
  collection; "Total Records" sums a column that is always 0;
* `/api/status`'s `status` field (read straight from that column at
  `statusapi.c:297`) and its `online/degraded/offline/working` summary are the
  same seed, so the iOS dashboard shows the same picture;
* the expanded row reads `src.recentLogs`, a key `/api/sources` never returns,
  so it always prints "No recent logs available" — while
  `GET /api/sources/:id/logs` exists and is called by nobody;
* the "Data Pipeline" strip prints a literal **ETL** box.

The real run history is in `fetch_log` (status, records_fetched, **stored**,
duration_ms, error — one row per run) and `source_sched_state`; the real
record counts are in `intel_items`. Both are already read by `/api/status`
and `/api/intel/sources`, just not by the page the nav calls "Sources".

### 1c. What the user asked to see, and whether the server can say it today

| wanted | where the fact lives | exposed? |
| --- | --- | --- |
| **Engine / mechanism** (how it fetches: URL template, entity tokens, POST body, headers, credential, index-page follow, charset, timeout, pacing) | `hp_source` row in memory (`lib/hpengine.c` `g_specs`, lookup is `static hp_lookup`); VJSON macro args compiled into static data; hand-written `run()` bodies | **No.** No serializer, no API, nothing in any payload says which engine runs a source |
| **Parsing** (mode, array_path, title/id/link/date/body/geo keys, csv delim, html table, detail hop) | same `hp_source` row | **No** |
| **Frequency** | `source_def.update_interval_sec` (declared), `source_sched_state` (effective, backoff, quarantine), `fetch_log` (actual cadence) | partly: `/api/status` only (`updateInterval`, `sched{}`); `/api/db/scheduler` is a 3-row cron table unrelated to sources |
| **Address / location** | `source_def.url` (portal), fetch host from the template, `core/hostgate.c` pacing (5 hosts), lat/lon of stored rows | portal only |
| **Obtained data and its form** | `intel_items`: record_type, properties keys, languages, dates, geo | counts only (`item_count`, geocoded); no record_type histogram, no field inventory, no sample |
| **Testing** | `fetch_log` rows; `collector-fetch-failure` / `-shape-` / `-truncation-` / `-status-notice` records; probe columns; batch verification TSVs under `docs/` | logs route exists but unused; notices are rows nobody surfaces per source; TSVs are files |
| **Status** | trust grade (`source_trust.c` from fetch_log + anomalies), sched state, credential status, quarantine | `/api/status` only, inside the 20 MB payload |
| **Size of data obtained** | `intel_items` row count; `fetch_log.records_fetched/stored` per run; **no byte count anywhere** | row count only |
| **Collector** | `source_def.collector` on every source (342 distinct names) | **Not in any payload.** `sources` table has no column; `/api/status` and `/api/intel/sources` omit it; iOS groups by `layer` instead and calls the rest "Uncategorised" |

### 1d. Collector names are half unassigned

`./bin/japanosint --list-sources` registers 18,883 sources in 342 collectors.
**9,872 (52%) are `osint`**, the default `hp_register()` substitutes when a row
has no `.collector` (`hpengine.c:4679`). 183 of 185 `pivot/table` files and
the generated `hp1x` tables set none (8,445 rows); the 615 `gnews-*` feeds and
326 hand-written literals make up the rest. The generator already accepts a
`collector` opt (`gen_hp_batch.py:113`); nobody used it. The natural grouping
for those rows is the table they live in (`hp3b25_jpmedia`, `hp3b30_jpscada`,
`hp3b23_jpmuni` …), which is also the beat the probe gates ran on.

The named 341 are mostly beat-level (`jp_prefectural` 178, `fr_prefectural`
121, `government` 535 …) with a long tail of 1-row collectors
(`bh_company-registry`, `au_ip` …). So "every source in a collector, some
alone, some grouped" is already the shape of the data; what is missing is the
naming of the 52% and a curated display layer over the machine keys.

### 1e. Scale constraints any revamp must respect

* 18,883 sources: list pages must be **server-paged and server-searched**.
  The dashboard currently sorts/filters all rows client-side; the intel tab
  fetches the whole list to find one id.
* `/api/status` full is 20 MB / 8 s (cached 10 s). It already supports
  `limit/offset/summary=1`; the summary form is cheap.
* The fleet routes run off the event loop on a worker thread with a response
  cache (`fleet_thread`, `respcache_*`). New routes must use the same pattern.
* The LLM path exists: `llm_init_suggest()` (small model via
  `LLM_SUGGEST_BASE_URL`, else `LLM_BASE_URL`), `llm_chat_ex()` with a status
  code for every failure, worker-thread + `mg_wakeup` dispatch
  (`/api/search/suggest`, `httpd.c:2054`). A summary route is a copy of that
  shape, not new machinery.
* Contract fixtures gate the SHAPE of `/api/status`, `/api/sources`,
  `/api/intel/sources`, `/api/layers`, `/api/intel/items` — adding fields is
  fine, removing or renaming is not. iOS decodes `sources` columns
  (`OsintSource`) and `/api/status` rows (`StatusRow`).

## 2. Plan

Four phases. Each is independently shippable and gated; later phases only
consume what earlier ones expose. Estimated sizes are for review, not promises.

### Phase 0 — the server says what it knows (C, no UI)

0.1 **`hp_describe_json(id)`** in `lib/hpengine.c` (+ `hpengine.h`): serialise
    the `hp_source` row as declared — every non-default field by name, enums
    as words (`mode: "json"`, `want: ["domain","ip"]`), plus derived facts the
    UI would otherwise re-derive: `kind` (`pivot` | `scheduled` | `both`),
    the entity tokens the URL/body use, the paging strategy as one word
    (`next_path` | `page_param` | `{page}` | `page_walk` | `single_request`),
    `detail_hop: true/false`, the fetch host. Header templates are shown
    verbatim — they carry `{env}` tokens, never values. Pinned by `hptest`.

0.2 **`engine` on `source_def`**: one new optional field. `hp_register` sets
    `"hpengine"`; `_verified_macros.inc` sets `"vjson"`/`"vrss"`/`"vgeo"` in
    the macro bodies (one line each); hand-written defaults to `"native"`.
    Cheap and exact, versus guessing from the run pointer.

0.3 **`GET /api/sources/:id/detail`** (new `core/sourceapi.c`), one source,
    built on a worker thread, cached 10 s by id:
    * `registry`: id, name, name_ja, collector, category, type, engine, portal
      url, description, license, layer, free_tier, declared interval;
    * `engine`: the 0.1 object for hpengine rows; for others, what the def
      says (url, interval) and `"detail": "hand-written run(); see <file>"`
      only if we can name the file (not known at runtime → omitted, honest);
    * `schedule`: declared, effective, backoff_until, quarantined, next due
      (computed from last run + effective interval), schedule_mode, runs 30d,
      success rate 30d, pivots say `on_demand` with the entity shapes wanted;
    * `credentials`: requiresKey / configured / missing env names (existing
      `add_cred_status`);
    * `status`: trust grade + reliability, consecutive failures/empties,
      anomalies 30d, latest `collector-fetch-failure` /
      `collector-shape-notice` / `collector-truncation-notice` /
      `collector-status-notice` per kind (title + properties, verbatim);
    * `data`: item_count, geocoded, awaiting geo, first/last fetched_at,
      min/max published_at, languages, record_type histogram (top 20, with
      `distinct_total` stated), properties key frequency over a sample of
      N most recent rows (N stated), bounding box of geocoded rows, stored
      bytes = `SUM(length(title)+length(body)+length(properties))`
      (measured, labelled "DB text bytes, not transfer size");
    * `runs`: last 20 `fetch_log` rows (timestamp, status, records_fetched,
      stored, duration_ms, error) + `total`, with `/api/sources/:id/logs`
      for paging;
    * `pacing`: hostgate entry for the fetch host if any;
    * `provenance` (optional, cheap because the binary carries
      `JO_REPO_ROOT`): the manifest line and verified/rejected/probe TSV rows
      whose first column is this id, read at request time; absent → `null`.

0.4 **`GET /api/sources/search`** — `q` (substring over id, name, name_ja,
    description, collector, fetch host), `collector`, `category`, `engine`,
    `kind` (scheduled|pivot), `status`, `grade`, `has_items`, `sort`,
    `limit`/`offset`. Answers `{data, page:{limit,offset,count,total,has_more},
    meta}` like every other list. Rows are compact (id, name, name_ja,
    collector, category, engine, interval, item_count, last_fetched, status,
    grade, sched flags). Built from the registry index + the same intel
    aggregate and sched tables `statusapi` already loads, off-loop, cached.

0.5 **`GET /api/collectors`** and **`GET /api/collectors/:name`**: per
    collector — label, description, parent (from 0.7), source count,
    scheduled/pivot split, items total, last fetched, status tallies,
    categories; the detail form lists its sources (paged, same row shape as
    0.4) grouped by `sub_source_id` / shared id prefix when one exists.

0.6 **Make `sources.status` true.** After `fetch_log_write()` in
    `core/scheduler.c` (and the on-demand run route), one UPDATE sets
    `status`, `last_check`, `last_success`, `response_time_ms`,
    `records_count`:
    `rc==0 && stored>0 → online`; `rc==0 && stored==0 → degraded`;
    `rc!=0 → offline`; never run stays `pending`. This repairs
    `/api/sources`, `/api/status`, the iOS dashboard and the web tiles in one
    place. Pinned by extending `test_sched_runline.c`. Alternative (not
    recommended): stop serving those columns — breaks iOS decoding.

0.7 **Collector naming.**
    * `HP_REGISTER_TABLE` passes `#TBL` into `hp_register`, which uses it as
      the default collector instead of `"osint"`. 8,445 rows gain a specific
      key (`hp3b25_jpmedia` …) with zero per-row edits; rows that already name
      one keep it. (`collector=` in `--list-sources` changes for those rows;
      `grep -rn 'collector=' native/tools tests` first — if any gate parses it,
      update that gate in the same change.)
    * `core/collectors.def`: curated `{key, label, label_ja, description,
      parent}` for display. Keys absent from the table render with the key as
      label, so a new beat is never hidden. The 342+ keys and their counts are
      in `collector-census-2026-10-11.tsv`; **which to merge under one parent
      (prefectural police, bus/transit portals, the `gnews-*` family, the
      1-row registries) is the decision this plan asks you to make** — the
      TSV is the worksheet. The default if you decide nothing: one collector
      per key, no parents.

Gates: `make` (0 warnings), `make hptest` (0.1), `make unit` (new
`test_source_describe.c`, `test_sources_search.c`, sched status write),
`make lint-sources`, `make source-floor registry-floor` unchanged (no
registration changes), `tests/contract/run.sh` (additive fields only).

### Phase 1 — Source detail page (web)

New route `/console/sources/:id` (`SourceDetailPage.jsx`), linked from every
place an id appears (dashboard rows, intel source page, collector pages, API
keys "used by"). One `useApi('/api/sources/:id/detail')` call. Sections, in
the order asked:

1. **Header** — name, name_ja, id, collector chip (link), category, type,
   engine, status badge, grade, portal link, **Run now** (reuses
   `POST /api/intel/sources/:id/run`; result rendered from the response).
2. **Summary (small model)** — `GET /api/sources/:id/summary` (Phase 1b).
3. **Engine & mechanism** — engine, mode, entity shapes, URL template with
   tokens highlighted, POST body, header templates, credential env +
   configured, index-page follow, charset, timeout, filter_query, hostgate
   pacing, JSONP/ndjson notes as the row declares them.
4. **Parsing** — array_path, title/id/link/date/body/geo keys (with the
   `+ composes, , chooses` reading spelled out next to `id_keys`), csv
   delimiter/comment/header, xlsx sheet, html href_must/base/table_must,
   detail hop (url/key/path/max and the `JO_HP_DETAIL_MAX` bound),
   date tokens / tz / date_back.
5. **Frequency** — declared vs effective interval, next due, backoff,
   quarantine, runs and success rate 30d, actual cadence from the last 20
   runs; pivots: "on demand, entity shapes: …".
6. **Address / location** — portal, fetch host, pacing, bbox of stored
   geocoded rows (drawn as numbers; a mini-map only if cheap).
7. **Obtained data and its form** — counts, record_type histogram,
   properties key inventory (with the sample size), 3 sample records (via
   `/api/intel/items?source=&limit=3`), languages, date range, DB text
   bytes; link to the full items page with search.
8. **Testing** — recent runs table (paged through `/api/sources/:id/logs`),
   latest notices verbatim, probe result if any (operator), provenance rows
   if found.
9. **Status** — status, grade/reliability, credential status, anomalies,
   quarantine, with the reason text the server gives.
10. **Size** — stored rows, last run fetched/stored, DB text bytes.

Every bounded list carries `BoundNote` (shown of total). Every `null` renders
as "not measured", never a dash that looks like zero.

**Phase 1b — `GET /api/sources/:id/summary`.** Builds a prompt from the 0.3
facts only (registry, engine, record_type histogram, field inventory, 3
sample titles), asks the suggest model (`llm_init_suggest`, `llm_chat_ex`,
JSON schema `{summary, result_type, caveats[]}`), on a worker thread with
`mg_wakeup`, cached by `(id, last_fetched_at, model)` in `respcache` and a
small `source_summary` table so a restart does not re-pay 18,883 prompts.
The response names the model and the fact count it was given. On any
`llm_status != OK` the body is `{error: <llm_status_code>, facts: …}` and the
card shows the facts under "model unreachable" — the summary is derived from
measured facts and is never fabricated to fill the slot.

Gates: `npx vitest run` (new `SourceDetailPage.test.jsx`: renders every
section from a fixture, shows "not measured" for nulls, shows the llm error
path), `npm run build`.

### Phase 2 — Sources list revamp (`/console/sources`)

* Replace the client-side table with a server-paged, server-searched list on

* Tiles and charts from `/api/status?summary=1` (cheap, cached) and

* `useDataSources` stops polling the 18,883-row `/api/sources` every 60 s for

Gates: `vitest` (search params round-trip to the URL, paging, empty/error
states), `vite build`.

### Phase 3 — Collectors list and UI

* `/console/collectors`: cards from `/api/collectors` — label, description,

  and sort; parents expand to children.
* `/console/collectors/:name`: the collector's sources (paged rows from 0.5),

* Nav: "Sources" keeps its entry; "Collectors" is added beside it under
  Operations. `/intel?view=sources` links across rather than duplicating.
* iOS follow-up (separate PR, if wanted): `StatusRow` decodes `collector` and
  `groupedAsCollectors()` groups on it instead of `layer`.

5. **Provenance from `docs/` TSVs at request time** (0.3 last bullet): in or

### 3b. Follow-up of 2026-10-12 (same branch)

Decisions confirmed: sources are grouped by **collector** and there is no
grouping OF collectors (no `parent` is set and none is planned); the iOS map's
layers are untouched.

* **Transfer bytes are recorded.** `http_client` counts every response body it
  receives (retries included) and the attempts; `scheduler_run_source()`
  writes `fetch_log.bytes_fetched` (new column, NULL on rows written before it
  = not measured) and the run line gains ` bytes=N requests=M` after
  `failed=`. The detail route reports `bytes_fetched` per recent run and
  `stats_30d.bytes_30d` + `runs_with_bytes_30d`; the Size section shows the
  last run's and the 30-day transfer, and says "predates byte accounting"
  for runs that have none.
* **`/api/status` rows carry `collector`, `collectorLabel`, `engine`,
  `kind`** (breach catalog rows: `_breach` / `Breach corpus` / `breach` /
  `corpus`). Additive; every existing key is unchanged.
* **iOS Sources dashboard groups by `collector`** (`groupedAsCollectors()`),
  so every one of the registered sources is in a visible group — it grouped by
  `layer`, which ~1% of sources declare, and put the rest under
  "Uncategorised". The group's name is the server's label when there is one,
  else the key; its category is the majority category of its sources. The
  "Refresh collector" button, which fetched a map LAYER named after the group,
