# Camera coverage investigation — 2026-08-01

**Question:** why are there so few cameras on the map — broken sources, stacked
points, or missing geocoding?

**Answer: all three, and a fourth nobody was looking for — the port silently
dropped every curated catalog the Node service shipped.**

Measured by running all camera sources into one database and counting distinct
positions rather than rows (`tests/audit/camera_audit.py`).

## 1. Stacking is the dominant problem

| | before | after restoring catalogs |
|---|---|---|
| camera rows | 1,350 | 1,529 |
| with coordinates | 1,350 | 1,529 |
| **distinct positions** | **562** | **734** |
| rows sharing a point | 788 (58%) | 795 (52%) |

**A map can only render distinct positions.** 1,350 rows were showing as ~562
pins. The worst offenders:

| point | cameras | what it is |
|---|---|---|
| 35.6762, 139.6503 | **176** | Tokyo prefecture centroid |
| 35.6895, 139.6917 | **122** | Tokyo Station |
| 34.6937, 135.5023 | 54 | Osaka centroid |
| 35.0116, 135.7681 | 23 | Kyoto centroid |
| 26.3344, 127.8056 | 20 | Okinawa centroid |

611 rows carry `location_precision: prefecture|city` + `location_approximate:
true` — they were never geocoded. Seven collectors
(`cam_camstreamer`, `cam_geocam`, `cam_skylinewebcams`, `cam_webcamera24`,
`cam_webcamtaxi`, `cam_worldcams`, `cam_worldcam_eu`) carry a
`PREFECTURE_CENTROIDS` table inherited verbatim from the Node service and fall
back to it whenever the aggregator page has no coordinate.

The contrast proves the mechanism, not the sources: `cam-worldcam_eu` gets
**156 rows / 155 distinct** and `public-cameras` (Overpass) **273 / 273**,
because those channels carry real per-camera coordinates.

## 2. The port dropped 179 cameras with exact coordinates — now restored

The Node service shipped curated catalogs of operator-published camera
positions. **None of it survived the port** — no C file contains any of these
coordinates. `bosai-volcano-cam`, which should have carried the JMA set, had
been reduced to a "is the portal up?" probe.

Restored as `cam-curated-jp` (`collectors/sources/cam_curated_jp.c`, generated by
`tests/audit/gen_curated_cams.py` straight from the deleted
`_cameraSources.js` in git):

| catalog | cameras |
|---|---|
| MLIT river monitoring | 96 |
| JMA volcano observation | 22 |
| Expressway traffic | 22 |
| Tourism live | 20 |
| Broadcast live | 15 |
| Manual IP | 4 |
| **total** | **179** |

Verified: `rc=0 records=179`, **179/179 with coordinates, 175 distinct
positions.** Every row carries `data_origin="curated-catalog"` and
`geo_precision="exact"` so it is distinguishable from centroid rows, and emits
through `camera_upsert()` into the shared camera keyspace (rows emitted via
`geojson_emit_features` are invisible to `camera_fc_json`).

These are real published station positions, not derived ones — the same data the
pre-port service served.

## 4. Node vs C — what else is missing

Node's `cameraDiscovery.js` fused **20 discovery channels**; the C port
registers 16 sources. Missing channels: `jma_volcano`, `mlit_river`,
`expressway_cctv`, `broadcast_livecam`, `tourism_webcam`, `manual_ip_seed`,
`earthcam`, `webcamendirect_seed` — all catalog-backed, now covered by
`cam-curated-jp`.

Also still unported from `_cameraSources.js`:

| catalog | entries | note |
|---|---|---|
| `CAMERA_DORKS` | 102 | search dorks for discovering exposed cameras |
| `SHODAN_CAMERA_QUERIES` | 98 | needs `SHODAN_API_KEY` |
| `OVERPASS_CAMERA_QUERIES` | 9 | partially covered by `public-cameras` |
| `AGGREGATOR_URLS` | 5 | aggregator index pages |
| `WEBCAMENDIRECT_SEED` | 5 | seed list |

The 102 dorks and 98 Shodan queries are the largest untapped discovery surface,
but both need credentials or a search backend.

## Recommended next steps, in value order

1. **Geocode the 611 centroid cameras.** `core/geoproxyapi.h` already exposes
   `geoproxy_geocode_forward(q, qAlt)` with a provider fallback chain — the same
   one `/api/geocode` uses. Resolving each camera's own place name would convert
   most of the 611 stacked rows into distinct pins. Best shape: a `_maint`
   enrichment pod (like `camera_stills.c`) that walks rows with
   `location_approximate=true` on a per-run budget and upgrades coordinates,
   rather than a network call inside `camera_upsert()`'s ingest path.
   **This is the single biggest remaining win — potentially +500 distinct pins.**
2. **Fix `cam-webcamtaxi`** — real scraper, upstream markup changed.
3. **Port `CAMERA_DORKS` / `SHODAN_CAMERA_QUERIES`** once a key is available.
4. **Consider dropping the centroid fallback entirely.** A camera at a
   prefecture centroid is arguably worse than a camera with no coordinate: it
   asserts a location that is wrong by tens of kilometres. It is at least
   flagged `approximate`, so the UI could filter it — that is a product call.
