# us-sf-311-open311-requests: the one collision that was real, measured

**2026-10-24.** The 136-row collision re-sweep
(`docs/measured-collisions-2026-10-24.tsv`) found 123 COLLISION rows totalling
1,284 records/pass, and argued all but one of them away from code: the
per-page collision guard content-hashes records that collide inside ONE page,
so a surviving collapse on a single-page row *proves* the records were
byte-identical, i.e. correct dedupe. One row was not covered by that argument:

```
us-sf-311-open311-requests  COLLISION  emitted 100  stored 66  db_rows 64  secs 164.4
```

`.id_keys = "service_request_id"` is unique by definition, the row is
`page_walk = 1` **and** `page_resume = 1` with no stable sort declared, and 34%
is two orders of magnitude above the 0.035% upstream-duplicate baseline this
tree measured for the detail-hop fleet. That is the shape the house rules call
the worst one — a collision that is really a skip, the visible half harmless
and the invisible half gone. It was left unfixed, because the stated fix was
"whichever sort parameter that Open311 server actually honours", and that is a
live measurement rather than an edit.

Here is the measurement. It was taken with three throwaway probe scripts
(rounds A–G, H–J and the attribution below) which are NOT in the repo — every
reading they produced is reproduced in this file, and each is one paced
`GET https://mobile311.sfgov.org/open311/v2/requests.json?…` that is quicker to
re-issue than to maintain. Paced at 1300 / 2600 ms against the 1200 ms gap
`core/hostgate.c` already holds for this host.

## The fix the rules prescribed does not exist

**The server honours no sort parameter at all.** Each of these is accepted with
HTTP 200 and returns the same result set as no parameter at all — rule 4d's
confident-wrong-answer shape, in the sort position:

| parameter | status | result set |
| --- | --- | --- |
| `sort=requested_datetime` | 200 | same as default |
| `order=asc` | 200 | same as default |
| `order_by=requested_datetime` | 200 | same as default |
| `sort_order=asc` | 429 | unmeasured (rate limit) |
| `zzz_not_a_param=1` | 200 | accepted and ignored, like the three above |

And there is no implicit order to lean on either. 20 records of the default
listing, in the order served:

```
18:10:50  16:58:51  18:11:35  18:11:35  16:57:51  17:21:43  01:55:50  18:11:14
18:07:23  18:09:42  21:52:45(Oct 23)   18:09:55  17:42:13  15:36:48  18:09:36
18:09:40  17:43:27  16:03:56  18:09:13  14:17:51
```

descending? **no.** ascending? **no.** The collection has no order.

What the server *does* honour, measured: `page` (page 1 ∩ page 9 = ∅),
`page_size` exactly, up to at least 200 — the row was asking for **5** — and
`start_date` / `end_date` / `updated_after` / `status`.

## The collision is a function of how long the walk takes

Walking the row's own 20 pages of 5 **fast** (26 s at 1300 ms):

```
pages=20  emitted=100  distinct=98  repeated=2
```

and the two repeats are adjacent across one page seam (page 19 ended with
`202000209778, 202000216558`; page 20 began with the same two) — a window
shifting by two while two new cases arrived.

The sweep's run of the same 20 pages took **164 s**, because it interleaves a
per-record detail hop paced at 1200 ms, and read 66 distinct of 100. SF files a
311 case about every 30 s and updates far more; a result set with no ORDER BY
is free to come back in a different order after any write, so the longer the
walk, the more the pages overlap and the more records are never served at all.

**This is why no `--run` could see it, and why `stored` alone cannot diagnose
it.** The same row, the same pages, the same engine: 98/100 in 26 s and 66/100
in 164 s. The sweep's own `secs` column is the diagnostic — a collision whose
size scales with the walk's duration is a reshuffle, not a key defect.

## A window over a past instant is the stable sort this server lacks

No case can acquire a `requested_datetime` that has already gone by, so a
dated window cannot reshuffle. Walked to its end on one finished day
(2026-10-20), `page_size=100`:

```
25 pages, every page n=100 and 100/100 in-window, last page n=29 (the
upstream's own end of data)
emitted=2429  distinct=2429  repeated=0
```

**2,429 of 2,429, every page disjoint.** The same window read twice returns the
identical set in the identical order, and the request with no `page` parameter
is byte-for-byte page 1, so the engine's 1-based detection resolves correctly
and the walk continues at page 2.

## The repair

`native/collectors/feed/generated/hp16_us_civilian_1.c`:

```
start_date={date-1d:%Y-%m-%dT00:00:00Z}&end_date={date+1d:%Y-%m-%dT00:00:00Z}&page_size=100&page=1
page_max = 80      (~49 pages needed; headroom, never equal to the need)
page_resume        REMOVED
```

Measured through the engine, three runs against fresh scratch databases:

| run | url | result |
| --- | --- | --- |
| before | `?page_size=5`, `page_resume` | `records=100 stored=66` — 34% collapsed |
| after | the window, no explicit `page` | `records=3890 stored=3783` — 107 collapsed |
| after | the window, `&page=1` | **`records=3836 stored=3823`** — 14 collapsed (0.36%) |

**100 records a run became 3,836, and the walk completes**: `emitted 3836 of
3836 available across 39 page(s)`, no truncation notice on the walk, no page
answered 429, and the database holds 3,823 rows / 3,823 distinct uids
(3,822 records + one detail-truncation notice).

* **48 hours, not 24.** The window must be wider than the 6 h interval, or
  cases filed after a day's last run fall between two windows and are never
  read at all.
* **`page_resume` is gone.** A cycle over an unordered collection is the
  defect, not a mitigation of it — and the engine refuses `page_resume` for a
  `{date…}` row anyway, since a stored position would pin one day forever.
* **`page_size` 5 → 100**, measured honoured (200 is too). The old value spent
  one request per 5 records.
* `page_max = 80` against ~49 pages needed, because a ceiling set exactly at
  the need manufactures a false truncation notice (this tree's `data.ca.gov`
  lesson).

## The engine's own 1-based probe reports as a UID-COLLISION of exactly one page

The 107 that remained after the window went in decomposes exactly, and only
one part of it was the upstream's:

```
run A: 3890 emitted, 3783 distinct records -> 107 collapsed   (39 pages)
run B: 1600 emitted, 1500 distinct records -> 100 collapsed   (17 pages, cut at page 16 by a 429)
```

**Exactly 100 in a run that read 16 pages, and 100 + 7 in a run that read 39.**
A constant that equals the page size, independent of how many pages were read,
is not an upstream property. It is ours: a `page_walk` row whose URL carries no
page number is fetched bare first, and the engine then requests `page=1` and
compares the two to decide whether the API is 0- or 1-based (the rule is in the
house rules). Those two responses are the same page — measured directly here,
identical ids in identical order, both 68,732 bytes — and **both are emitted**,
so every such run re-emits its first page and reports one page_size worth of
collapse.

Nothing is lost by it: the second copy is byte-identical to the first, so the
collapse is correct dedupe. What it costs is the one request, and the
diagnostic value of the metric — it puts a floor of one page size under the
UID-COLLISION count of every paged row that does not bind its own page
parameter, which is the number this tree uses to find real loss. Binding
`&page=1` in the URL removes it: 107 → 14, and one fewer request per run
(97 against 104).

**So when reading a COLLISION verdict: a collapse equal to the row's page size
is this, not a key defect.** 14 of 3,836 remains, and that part is the
upstream's own: read fast, the same 48 h window gives 10 repeated ids out of
3,804 and **all ten are byte-identical both times** (0.26%). The frozen half
alone gives 2 of 2,440, also byte-identical.

## Still open

* **The host's rate limit bites this walk sometimes, and the right gap is not
  measured.** Of three engine runs of the 39-page walk at the 1200 ms gap
  `core/hostgate.c` holds for this host, two completed all 39 pages with no
  429 and one was cut at page 16 by a 429 carrying `Retry-After: 35`. The cut
  is disclosed — `(TRUNCATED: a later page failed — page 17 answered 429)` —
  so rule 2 holds, but a third of the window is missing from that run. The
  remedy is a wider gap, and this file's own rule is that a gap is a
  measurement rather than a guess: finding it means bisecting the host's
  budget, which was not done here because ~250 requests had already gone to it
  today and a reading taken against a spent budget is a reading of the
  afternoon, not of the host. Worth noting the detail hops compete for the
  same gap — 97 requests a run, of which 39 are pages.
* **The detail hop now reaches far fewer records, and that is the deliberate
  trade.** 100 records a run all got their detail hop; 3,836 do not — ~60 are
  fetched inside the 120 s detail budget and the rest carry `_detail_pending`
  with a `collector-truncation-notice` naming the counts. It costs little
  here, because this upstream's LIST record already carries the whole case:
  the free-text `description`, `status`/`status_notes`, `lat`/`long`,
  `address`, `media_url` and both timestamps are all in the list response
  (observed). A row whose list record were a stub would want the opposite
  trade.
* **Cases REQUESTED before the window but UPDATED inside it** are not re-read.
  `updated_after` is honoured and would catch them, but a window on
  `updated_datetime` is not frozen — a case updated mid-walk enters it — so it
  carries the same reshuffle hazard and wants its own measurement before being
  used as a second row.
