# us-sf-311-open311-requests: the one collision that was real, measured

**2026-10-24.** The 136-row collision re-sweep
(`docs/measured-collisions-2026-10-24.tsv`) found 123 COLLISION rows totalling
1,284 records/pass, and argued all but one of them away from code: the
per-page collision guard content-hashes records that collide inside ONE page,
so a surviving collapse on a single-page row *proves* the records were
byte-identical, i.e. correct dedupe. One row was not covered by that argument:

```
us-sf-311-open311-requests  COLLISION  emitted 100  stored 66  db_rows 64  secs 164.4
```

`.id_keys = "service_request_id"` is unique by definition, the row is
`page_walk = 1` **and** `page_resume = 1` with no stable sort declared, and 34%
is two orders of magnitude above the 0.035% upstream-duplicate baseline this
tree measured for the detail-hop fleet. That is the shape the house rules call
the worst one — a collision that is really a skip, the visible half harmless
and the invisible half gone. It was left unfixed, because the stated fix was
"whichever sort parameter that Open311 server actually honours", and that is a
live measurement rather than an edit.

Here is the measurement. It was taken with three throwaway probe scripts
(rounds A–G, H–J and the attribution below) which are NOT in the repo — every
reading they produced is reproduced in this file, and each is one paced
`GET https://mobile311.sfgov.org/open311/v2/requests.json?…` that is quicker to
re-issue than to maintain. Paced at 1300 / 2600 ms against the 1200 ms gap
`core/hostgate.c` already holds for this host.

## The fix the rules prescribed does not exist

**The server honours no sort parameter at all.** Each of these is accepted with
HTTP 200 and returns the same result set as no parameter at all — rule 4d's
confident-wrong-answer shape, in the sort position:

| parameter | status | result set |
| --- | --- | --- |
| `sort=requested_datetime` | 200 | same as default |
| `order=asc` | 200 | same as default |
| `order_by=requested_datetime` | 200 | same as default |
| `sort_order=asc` | 429 | unmeasured (rate limit) |
| `zzz_not_a_param=1` | 200 | accepted and ignored, like the three above |

And there is no implicit order to lean on either. 20 records of the default
listing, in the order served:

```
18:10:50  16:58:51  18:11:35  18:11:35  16:57:51  17:21:43  01:55:50  18:11:14
18:07:23  18:09:42  21:52:45(Oct 23)   18:09:55  17:42:13  15:36:48  18:09:36
18:09:40  17:43:27  16:03:56  18:09:13  14:17:51
```

descending? **no.** ascending? **no.** The collection has no order.

What the server *does* honour, measured: `page` (page 1 ∩ page 9 = ∅),
`page_size` exactly, up to at least 200 — the row was asking for **5** — and
`start_date` / `end_date` / `updated_after` / `status`.

## The collision is a function of how long the walk takes

Walking the row's own 20 pages of 5 **fast** (26 s at 1300 ms):

```
pages=20  emitted=100  distinct=98  repeated=2
```

and the two repeats are adjacent across one page seam (page 19 ended with
`202000209778, 202000216558`; page 20 began with the same two) — a window
shifting by two while two new cases arrived.

The sweep's run of the same 20 pages took **164 s**, because it interleaves a
per-record detail hop paced at 1200 ms, and read 66 distinct of 100. SF files a
311 case about every 30 s and updates far more; a result set with no ORDER BY
is free to come back in a different order after any write, so the longer the
walk, the more the pages overlap and the more records are never served at all.

**This is why no `--run` could see it, and why `stored` alone cannot diagnose
it.** The same row, the same pages, the same engine: 98/100 in 26 s and 66/100
in 164 s. The sweep's own `secs` column is the diagnostic — a collision whose
size scales with the walk's duration is a reshuffle, not a key defect.

## A window over a past instant is the stable sort this server lacks

No case can acquire a `requested_datetime` that has already gone by, so a
dated window cannot reshuffle. Walked to its end on one finished day
(2026-10-20), `page_size=100`:

```
25 pages, every page n=100 and 100/100 in-window, last page n=29 (the
upstream's own end of data)
emitted=2429  distinct=2429  repeated=0
```

**2,429 of 2,429, every page disjoint.** The same window read twice returns the
identical set in the identical order, and the request with no `page` parameter
is byte-for-byte page 1, so the engine's 1-based detection resolves correctly
and the walk continues at page 2.

## The repair

`native/collectors/feed/generated/hp16_us_civilian_1.c`:

```
start_date={date-1d:%Y-%m-%dT00:00:00Z}&end_date={date+1d:%Y-%m-%dT00:00:00Z}&page_size=100&page=1
page_max = 80      (~49 pages needed; headroom, never equal to the need)
page_resume        REMOVED
```

Measured through the engine, three runs against fresh scratch databases:

| run | url | result |
| --- | --- | --- |
| before | `?page_size=5`, `page_resume` | `records=100 stored=66` — 34% collapsed |
| after | the window, no explicit `page` | `records=3890 stored=3783` — 107 collapsed |
| after | the window, `&page=1` | **`records=3836 stored=3823`** — 14 collapsed (0.36%) |

**100 records a run became 3,836, and the walk completes**: `emitted 3836 of
3836 available across 39 page(s)`, no truncation notice on the walk, no page
answered 429, and the database holds 3,823 rows / 3,823 distinct uids
(3,822 records + one detail-truncation notice).

* **48 hours, not 24.** The window must be wider than the 6 h interval, or
  cases filed after a day's last run fall between two windows and are never
  read at all.
* **`page_resume` is gone.** A cycle over an unordered collection is the
  defect, not a mitigation of it — and the engine refuses `page_resume` for a
  `{date…}` row anyway, since a stored position would pin one day forever.
* **`page_size` 5 → 100**, measured honoured (200 is too). The old value spent
  one request per 5 records.
* `page_max = 80` against ~49 pages needed, because a ceiling set exactly at
  the need manufactures a false truncation notice (this tree's `data.ca.gov`
  lesson).

## The engine's own 1-based probe reports as a UID-COLLISION of exactly one page

The 107 that remained after the window went in decomposes exactly, and only
one part of it was the upstream's:

```
run A: 3890 emitted, 3783 distinct records -> 107 collapsed   (39 pages)
run B: 1600 emitted, 1500 distinct records -> 100 collapsed   (17 pages, cut at page 16 by a 429)
```

**Exactly 100 in a run that read 16 pages, and 100 + 7 in a run that read 39.**
A constant that equals the page size, independent of how many pages were read,
is not an upstream property. It is ours: a `page_walk` row whose URL carries no
page number is fetched bare first, and the engine then requests `page=1` and
compares the two to decide whether the API is 0- or 1-based. Those two
responses are the same page — measured directly here, identical ids in
identical order, both 68,732 bytes — and both were emitted, so every such run
re-emitted its first page and reported one page_size worth of collapse.
Binding `&page=1` in the URL removes it for this row: 107 → 14, and one fewer
request per run (97 against 104).

### Why it was emitted twice, which is not what this file first said

The first version of this section stopped at "both are emitted", as though the
engine did that unconditionally. **It does not, and the reason it happened
anyway is the part worth keeping.** Both walks already guard against it and the
guard runs BEFORE the emit — `lib/jsonlist.c` says so in as many words ("This
check MUST run before the emit below. It used to run after…", measured
2026-09-05, 129 of 882 sources sitting at an exact 1/2 or 1/3 ratio) and
`lib/hpengine.c` carries the same branch, enabled for this row. The probe
should have been recognised and dropped. The question this file did not ask is
why it was not.

Two lines of the engine answer it. The probe's verdict rested on
`jsonlist_page_fp()` — an **order-sensitive hash of a page's first EIGHT
records** — and `hp_emit_record` **spends the detail budget per record inside
the page loop**. So on this row the bare request and the `page=1` request are
not 1.2 s apart: the 58 detail hops of page 1 run between them, ~70 s at this
host's 1200 ms gap. Against a collection with no ORDER BY and a live edge, the
first eight records are not the first eight any more. The hash missed, the
probe read as new data, and the whole page was emitted again — which is also
why the two responses looked byte-identical to the probe script above and not
to the engine: that script issued them 2.6 s apart.

**So the generalisation this file drew was too broad.** It said a floor of one
page size sits under "every paged row that does not bind its own page
parameter". It does not. It sits under the rows whose SECOND request is delayed
far enough for the collection to move — a detail hop per record, or a slow
host — and a fast walk over a stable collection has the probe caught correctly,
as it always did. Two further conditions narrow it again: the first page must
come back FULL, or the walk stops before a probe is ever issued (measured on
`us-austin-apd-crime-arcgis`: 297 records against a page size of 1,000, one
page, no probe), and the row must not bind its own page number. Of the 351
hpengine rows declaring an ArcGIS/WFS page size with a page parameter, **three
also declare a `detail_url`** — `CA_CALGEM_WELLS`, `IMF_PORTWATCH_PORTS`,
`IMF_PORTWATCH_CHOKEPOINT_DAILY`, all at `page_size=1000`, so where it fires
there it is a thousand records, not a hundred (measured by the session that
added that pager family, 348 of 351 rows located).

### The fix, and where it belongs

In the probe's decision, not in a row. `jsonlist_page_one_retry()` already
answers "is this request the 0-vs-1-based probe?" from the URL pair alone,
deterministically, and a reorder cannot touch a URL — so that is what is asked
now, and the 0-vs-1-based question is settled by record IDENTITY: each record's
own content fingerprint, sorted, compared as a set (`jsonlist_page_fps()`).

The page is **not** skipped wholesale, and that is the half worth stating. A
case that arrived between the probe's two requests is on that response and on
nothing we have read, so dropping the page would discard it — rule 2. The probe
emits the records the previous page did not carry and skips the ones it did.
Both walks carry it (`hpengine.c`'s `hp_run_json` and
`jsonlist_emit_paged`), because this tree's rule about looking for the other
copies of a bug applies to a bug in a shared decision too. `hptest` 28c/28d and
31e are this server modelled offline — a page 1 re-served in the opposite order,
and one with a new record at its head — and they fail on the hash and pass on
the identity set.

Binding `&page=1` in the row's URL stays: with the engine fixed it is no longer
load-bearing, but it saves a request a run and is a true statement about a
server measured to be 1-based.

**So when reading a COLLISION verdict: a collapse equal to the row's page size
on a walk whose second request was slow is this, not a key defect.** 14 of
3,836 remains, and that part is the upstream's own: read fast, the same 48 h
window gives 10 repeated ids out of 3,804 and **all ten are byte-identical both
times** (0.26%). The frozen half alone gives 2 of 2,440, also byte-identical.

## Still open

* **The host's rate limit bites this walk sometimes, and the right gap is not
  measured.** Of three engine runs of the 39-page walk at the 1200 ms gap
  `core/hostgate.c` holds for this host, two completed all 39 pages with no
  429 and one was cut at page 16 by a 429 carrying `Retry-After: 35`. The cut
  is disclosed — `(TRUNCATED: a later page failed — page 17 answered 429)` —
  so rule 2 holds, but a third of the window is missing from that run. The
  remedy is a wider gap, and this file's own rule is that a gap is a
  measurement rather than a guess: finding it means bisecting the host's
  budget, which was not done here because ~250 requests had already gone to it
  today and a reading taken against a spent budget is a reading of the
  afternoon, not of the host. Worth noting the detail hops compete for the
  same gap — 97 requests a run, of which 39 are pages.
* **The detail hop now reaches far fewer records, and that is the deliberate
  trade.** 100 records a run all got their detail hop; 3,836 do not — ~60 are
  fetched inside the 120 s detail budget and the rest carry `_detail_pending`
  with a `collector-truncation-notice` naming the counts. It costs little
  here, because this upstream's LIST record already carries the whole case:
  the free-text `description`, `status`/`status_notes`, `lat`/`long`,
  `address`, `media_url` and both timestamps are all in the list response
  (observed). A row whose list record were a stub would want the opposite
  trade.
* **Cases REQUESTED before the window but UPDATED inside it** are not re-read.
  `updated_after` is honoured and would catch them, but a window on
  `updated_datetime` is not frozen — a case updated mid-walk enters it — so it
  carries the same reshuffle hazard and wants its own measurement before being
  used as a second row.

## 2026-10-25: the window sized to the cadence, and the rest of this host

The 48 h window above was right about the hazard and wrong about the price. It
is wider than the 6 h cadence by a factor of eight, so every case was read
about eight times, at 39 pages a run — and the host's 429 landed on page 17 of
one walk in three. The remedy named here was a wider hostgate gap. The cheaper
one is to stop asking for 39 pages.

Measured against the live server, 9 requests:

| question | reading |
| --- | --- |
| is `start_date` honoured at HOUR granularity, or truncated to the date? | **honoured**: asked `>= 00:25:01Z`, oldest record served `00:53:08Z`, nothing from before the instant (a truncating server would have served from `00:00Z`) |
| how big is an 8 h window? | **6 pages, 521 records, 0 repeats, 21 s** |
| how many service codes does `services.json` list? | **8** |
| does the frozen case id in `us-sf-311-open311-request-detail` still exist? | **yes** — requested 2026-08-16, status `closed` |

So the window is now **`start_date={ago:43200}`, a rolling twelve hours**:
`lib/datetok.c` renders that token as `%Y-%m-%dT%H:%M:%SZ`, which is the exact
spelling measured honoured. Twelve rather than eight because the window has to
survive a MISSED run: at 12 h against a 6 h cadence there are two full runs of
slack, at 8 h only two hours. `page_max` is 40 against ~13 pages needed.

Then the row itself, through the engine, against a fresh scratch database:

```
emitted 1074 of 1074 available across 11 page(s)
records=1074 stored=1074 notices=1 requests=59 147483ms
UID-COLLISION: 1 of 1074
```

**The walk completes, and the walk is 11 pages instead of 39.** `stored` 1074 is
1,073 records plus one disclosure, so one record of 1,074 collapsed (0.09%,
against the 0.26% upstream-duplicate baseline measured here yesterday). 59
requests a run against 97. No page answered 429 — the walk no longer reaches
page 17, which is where it was being refused. Some DETAIL hops still answer 429
and the per-run detail notice says so; that trade is unchanged and the second
"Still open" item above still describes it.

**The hostgate gap is no longer the open question for this row**, which is
better than a measured gap: the walk that provoked the refusal does not exist
any more. A gap may still be worth measuring for the detail hops, and that is a
different measurement from the one this file left open.

### The other two rows on this host, measured rather than estimated

Reading the file rather than the row first produced an arithmetic estimate of
~800 requests a day to `mobile311.sfgov.org` from three scheduled rows, on the
assumption that `us-sf-311-open311-services` fans a detail hop out over ~100
service codes. **The catalogue holds 8.** So that row costs 9 requests a run,
not ~100, and the host's real total is about 108 per 6 h cycle across the three
rows — 59 for the window row, 9 for the catalogue, 2 for the single-case row
— roughly 430 a day. An estimate from a shape is not a measurement, even when
the shape is read correctly.

The single-case row is a genuine finding and is left alone deliberately:
`us-sf-311-open311-request-detail` has `.url` pointing at ONE hardcoded case id
with `interval = 21600`, so it re-reads one case four times a day forever, and
that case was filed 2026-08-16 and is `closed` — it will never change again.
Its own name and description ("single service request", "full record for one
case id") say it was meant to be a lookup. It cannot simply become one: an
entity pivot needs an entity token AND, under `core/osint_dispatch.c`'s
`is_entity_pivot()`, a collector label the dispatcher recognises, so dropping
the interval to 0 under `collector = "us_civilian"` would make it a NEVER-RUNS
row and fail `make registry-floor` — which is exactly the openFDA shape this
tree already records ("that repair landed and did nothing"). The fix is a
registration change with a collector relabel behind it; it wants its own
measurement and its own commit, not a hitchhike on this one.
