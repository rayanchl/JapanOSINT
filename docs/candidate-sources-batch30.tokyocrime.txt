# Batch 30 - tokyocrime: the Tokyo Metropolitan Police (警視庁) statistics section, which no row in the tree reached before.
#
# Every count below was fetched live with curl -A 'JapanOSINT/1.0' on 2026-09-21 and read out of the file itself.
# 82 rows across the three published series: 361030 records, 360555 predicted stored.
# MEASURED 2026-09-21 through the real binary (audit_registry_emit, all 82 rows): 361030 emitted,
# 360559 stored, 471 lost, 0 unexplained. Emitted matched the prediction exactly; stored came in FOUR
# above it, which is the aggregate-file case described in the correction below - a shared 市区町丁 key
# whose rows differ is KEPT, not collapsed. Every one of the 471 was matched to a duplicate measured in
# the file itself. Per-row results: docs/verified-sources-batch30.tokyocrime.tsv.
#
# Why the two numbers differ, stated up front so nobody 'fixes' a non-bug (rule 4b): the 475-record gap is
# duplicates that are BYTE-IDENTICAL across every column - the same village or the same incident published
# twice. hpengine's in-page collision guard content-hashes records that collide on a key, so records that
# merely share a key are all kept while byte-identical ones collapse. That is real dedupe, and each CSV is a
# single fetch, so the guard covers the whole file.
#
# CORRECTION, measured 2026-09-21 after the first run through the engine. That holds for the 65 incident
# files and is only a LOWER BOUND for the 17 aggregate ones, because the two sets were counted with
# different metrics and the difference is exactly the thing rule 4b is about. For the incident files
# "distinct" above means distinct WHOLE LINES, which is what the guard ends up keying on, and every one of
# those predictions held exactly: BICYCLE_2024 28831/28779, ZENCHO_R7 5629/5608, PARTS_2021 1404/1402.
# For the aggregate files it means distinct 市区町丁 - the KEY, not the record. Where two rows share a
# chome name but differ in their counts, the guard disambiguates them by content hash and keeps BOTH, so
# stored comes in ABOVE the figure written here. R8.csv is that case: 西多摩郡檜原村 appears twice with
# totals 8 and 10, and the row stored 5156 of 5156 with no UID-COLLISION line at all, one more than the
# 5155 predicted. R5.csv and R7.csv carry the byte-identical kind (檜原村 and 神津島村 repeated with every
# column equal) and collapse as described. The rule, stated properly: stored >= distinct-key, and
# stored == distinct-record. A number here that is one or two low is that, not a discard.
#
# id_keys uses '+' throughout: '+' JOINS and ',' CHOOSES. These files carry no id column, so identity is the
# tuple of every dimension the file publishes. hp_pick_s copies id_keys into buf[512]; the longest key here is
# 252 bytes, and an over-long COMPOSITE is replaced by its FNV hex rather than truncated, so neither silently
# manufactures collisions.
#
# These endpoints were recorded as DEAD in docs/rejected-sources-batch28.jppolice.tsv under
# 'DNS resolution failure'. The observation was right and the conclusion was wrong: the host recorded there is
# www.keishicho.metro.tokyo.jp, which really is NXDOMAIN, while the site is served from
# www.keishicho.metro.tokyo.lg.jp. A missing .lg retired five real sources; that TSV is corrected alongside
# this manifest.
